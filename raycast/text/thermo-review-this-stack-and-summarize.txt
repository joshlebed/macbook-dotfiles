```
# PR Review Brief

You are an independent, read-only code reviewer. Do not modify files, push, merge, open PRs, post GitHub/Slack comments, associate this task with the PR, or implement fixes. 

Your job is to review this PR and write a report.

PR link: https://github.com/<owner>/<repo>/pull/<n>. Do not merge. Author: <author name> (<login>). Title: <title>.

Review the PR's current head against its current base. Write the head SHA you reviewed in the first line of your report.

Your report will consist of three parts.

## Review Part 1: PR Summary

The first part of your report will be a brief summary of the PR. The target audience for this part is someone with less intimate familiarity with the PR, who hasn't read or written the code.

The shape of the PR summary will depend on the nature of the PR. Some PRs are more complex, and some are more simple. Some are UX/product changes, some are backend/infra changes, some are ops changes, and there are many more possibilities which can be explained in different optimal ways. Generally, you should follow this format and deviate as necessary to suit the type of changes that you're reviewing. The most important part of the PR summary is that it is easy to understand for someone who does not have much context on the code changes or the reason why the PR was written. The PR Summary should answer these questions:

1. what is this PR changing?
2. what problem is it solving?

Target 50 words total for the PR Summary:

1. one or two sentences of context: the problem at hand and/or what a newcomer needs to know. include high level context that might seem obvious if you've read or written the PR, but a newcomer might not know.
2. one or two sentences explaining what the PR actually does: what components of the system are being added/removed/modified, what behaviors of the system will change, what data structures or information flows are new or changed.
3. optionally, explain what the PR does not do. if the PR is a foundation PR preparing for another PR, make it clear what is NOT included in this PR. if this does not add value, leave it out.

include these techniques when they are useful in the PR Summary:

* "a -> b -> c" for data flow
* numbered lists for sequences
* bullets for sets
* before/after comparisons of the system behavior before and after the PR

## Review Part 2: Technical Deep Dive

This is your opportunity to explore one or two of the more interesting/critical/controversial pieces of the PR that are highest leverage for a reviewer to understand. The deep dive section might be very short if the PR is very simple or small. The Technical Deep Dive should answer these questions:

* what is the most important interface or API changing in the PR?
* what is the biggest complexity in this PR?
* what is the most controversial design decision in this PR?
* what are the biggest risks of shipping this PR to customers?

You can structure this section however you want. If there are data structures being introduced or changed, focus on that and present the structures as pseudocode and/or with simple diagrams. If data flows are changing, focus on that and use simple text-based diagrams or simple mermaid diagrams if they are helpful.

Importantly, this section should be less than 200 words. it should be clearly organized, and a reviewer without context on the PR should be able to read and understand it in less than 3 minutes. Getting this section right is critical to preparing for the Thermo Review, so the findings have context.

## Review Part 3: Thermo Review

Read .claude/skills/thermo-nuclear-code-quality-review/SKILL.md and use it to review the PR.
Be thorough. Write this part of the report output format suggested by /thermo-nuclear-code-quality-review. 
Focus especially on APIs, types, interfaces, new data structures, and new data flows.
Your thermo report should go in a section titled "## Thermo Review".
Ensure that concepts and terms you use in your thermo review are understandable based on the PR summary. If they're not, explain them.

# Style Guidance

For all 3 parts of your review, write in Simplified Technical English (ASD-STE100).

Follow these rules:

- Use common, precise words.
- Use each word with one meaning.
- Use the same term for the same item or action.
- Use active voice when it makes the instruction clear.
- Use short sentences. Prefer 20 words or fewer.
- Put one main instruction or idea in each sentence.
- Avoid idioms, slang, metaphors, and unnecessary modifiers.
- Make references explicit. Avoid unclear pronouns such as "it," "this," or "they."
- Use lists for procedures, options, or groups of related facts.

# Delivery

Write the complete three-part report as your final message in this task. Do not shorten it to a summary.
Do not call send_followup or message any task, including the task that created you. The reader opens this task to read the report.
```
